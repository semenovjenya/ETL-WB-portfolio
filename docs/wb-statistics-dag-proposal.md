# WB API: Схема DAG для накопления статистики

> Предложение по архитектуре DAG и БД для сбора всех данных, влияющих на продажи, с последующим обогащением и передачей в ML.

---

## 1. Лимиты по дням (из RAG)

Результаты запросов к RAG в pgvector (localhost:55433). Запуск: `python scripts/rag_query.py`

|----------|----------|
| GET /api/v1/acceptance_report | Отчёт о платной приёмке |
| GET /api/v1/analytics/goods-labeling | Штрафы за маркировку |
| GET /api/v1/analytics/goods-return | Возвраты товаров |
| GET /api/v1/analytics/region-sale | sales по регионам стран |

| Endpoint | Описание |
|----------|----------|

| Endpoint | Описание |

## 2. DAG-схема для выгрузки (по лимитам)

```
┌──────────────┐
│ start        │
└──────┬───────┘
       │
       ├── ГРУППА A: Лимит 31 день
       │   • acceptance_report
       │   • analytics/goods-return
       │   • analytics/goods-labeling
       │   • analytics/region-sale
       │   chunks: по 31 день
       │
       ├── ГРУППА B: Лимит 8 дней
       │   • paid_storage
       │   chunks: по 8 дней
       │
       ├── ГРУППА C: Лимит 365 дней
       │   • analytics/brand-share
       │   • analytics/brand-share/parent-subjects
       │
       ├── ГРУППА D: Лимит 7 дней
       │   • search-report/product/orders
       │   • sales-funnel/products_history
       │
       └── ГРУППА E: 90 дней хранения (supplier)
           • supplier/sales
           • supplier/orders
           • supplier/stocks (dateFrom для пагинации)
           schedule: инкрементально
```

| Группа | Макс. период | Шаг окна |
|--------|--------------|----------|
| A | 31 день | 31 день |
| B | 8 дней | 8 дней |
| C | 365 дней | 365 дней |
| D | 7 дней | 7 дней |
| E | 90 дней хран. | инкрементально по dateFrom |

## 3. Цель: полная БД для витрины и ML

Собирать всё, что влияет на продажи:

- маркетинг
- поиск
- промо
- позиция в каталоге и её динамика
- CPC, CPM
- цена и динамика цены

---

## 4. Домены и факторы влияния

```
sales (результат)
    ↑
    ├── Поиск: позиция в выдаче, запросы, CTR
    ├── marketing: РК, CPC/CPM/CTR, бюджеты
    ├── Промо: участие в акциях, скидки
    ├── Цена: цена, история цен, скидки
    ├── Каталог: остатки, наличие
    ├── Карточка: рейтинг, отзывы
    └── Контекст: регион, склад, тарифы
```

| Домен | Что влияет на продажи | Endpoints WB |
|-------|------------------------|--------------|
| sales | Объём, выручка, возвраты | supplier/sales, supplier/orders, reports |
| Поиск | Позиция, запросы, переходы | search-report, product/orders, sales-funnel |
| Реклама | Показы, клики, CPC, CPM | adv/v1/stats, normquery/stats |
| Промо | Участие, скидки, акции | calendar/promotions, excise-report |
| Цена | Текущая, история, скидки | content (карточки), цены |
| stocks | Наличие, FBW/FBS | supplier/stocks, warehouse_remains |
| supplies | Пополнение | supplier/incomes |
| Возвраты | Выручка, логистика | analytics/goods-return |
| Каталог | nmId, subject, brand | content, directories |
| tariffs | Рентабельность | tariffs, commission |

## 5. Слои данных

### Справочники (dimensions)

Загружаются первыми, мало зависят от даты:

- Товары (nmId, subject, brand)
- Склады, офисы
- Категории, теги
- tariffs

### Факты по периодам (facts)

Обновляются по dateFrom/dateTo:

- sales, заказы
- Позиция в поиске
- Реклама
- stocks (срезы)

### События / транзакции

Одна строка = одно событие:

- supplies, приёмка
- Изменения цен, участие в промо

```
        └──────────────────┼────────────────────┘

                ┌─────────────────────┐
                │ stocks, цены, промо│
                │ stocks, prices, ... │
                └─────────────────────┘
```

## 8. Важно для ML

1. **Единый grain** — nmId + date + request/warehouse для объединения таблиц
2. **Согласованность дат** — одна и та же календарная дата для всех метрик
3. **Задержки WB** — разные отчёты обновляются с разной скоростью (30 мин, 1 час, несколько дней)
4. **Хранение** — supplier/sales и supplier/orders доступны только 90 дней, историю нужно накапливать самим
